     1→# FSOC-PAT Frontend Design Specification
     2→
     3→## 0. Document Purpose
     4→
     5→This document is the frontend source of truth for the FSOC-PAT application:
     6→
     7→**AI-Assisted Virtual Camera Tracking System for Coarse Alignment of Mobile Free Space Optical Communication (FSOC) Terminals**
     8→
     9→The frontend shall be implemented as a **professional Next.js desktop web interface** for the local simulation/control application or as the visual shell around the Python/PySide6 engine through a future bridge.
    10→
    11→The design goal is not to look like a generic "AI dashboard", a SaaS landing page, or a vibecoded prototype.
    12→
    13→It must look like a **real aerospace/optical tracking operations console**: restrained, technical, information-dense, precise, calm, and credible.
    14→
    15→The UI should communicate:
    16→
    17→> "This is a serious engineering instrument used to develop and validate an optical coarse-pointing algorithm."
    18→
    19→The frontend must make it visually obvious that the system is actually working:
    20→- the beacon is moving,
    21→- the camera is moving,
    22→- the detector is finding the beacon,
    23→- the tracker is predicting it,
    24→- the controller is generating pan/tilt commands,
    25→- disturbances are affecting the scene,
    26→- and the measured performance is improving or degrading.
    27→
    28→---
    29→
    30→# 1. Product Design Principles
    31→
    32→## 1.1 Primary Principles
    33→
    34→### Instrument, not website
    35→
    36→The application should feel like instrumentation software, not a marketing website.
    37→
    38→Avoid:
    39→- giant hero sections,
    40→- excessive rounded cards,
    41→- excessive gradients,
    42→- glowing neon everywhere,
    43→- random glassmorphism,
    44→- fake 3D illustrations,
    45→- excessive icon usage,
    46→- unnecessary animations.
    47→
    48→Use:
    49→- strong hierarchy,
    50→- measured spacing,
    51→- thin technical borders,
    52→- restrained surfaces,
    53→- precise typography,
    54→- data visualization,
    55→- functional controls,
    56→- meaningful motion.
    57→
    58→### Evidence over decoration
    59→
    60→Every visual element should answer one of these questions:
    61→
    62→1. Where is the beacon?
    63→2. Is it detected?
    64→3. Is it being tracked?
    65→4. Where is the virtual camera pointing?
    66→5. How much error exists?
    67→6. What disturbance is active?
    68→7. Is the system inside the PS-169 target?
    69→8. What happened during this run?
    70→
    71→### Spatial hierarchy
    72→
    73→The screen must visually prioritize:
    74→
    75→1. Camera viewport
    76→2. System state
    77→3. Tracking/performance metrics
    78→4. Scenario/control configuration
    79→5. Event logs
    80→
    81→The camera viewport is the primary canvas.
    82→

    85→# 2. Overall Visual Direction
    86→
    87→## 2.1 Theme
    88→
    89→**Professional dark aerospace laboratory theme**
    90→
    91→Base:
    92→
    93→- Background: near-black charcoal, not pure black
    94→- Primary surfaces: dark graphite
    95→- Secondary surfaces: slightly elevated graphite
    96→- Borders: neutral low-contrast gray
    97→- Text: soft white
    98→- Secondary text: cool gray
    99→- Positive status: restrained green
   100→- Warning: amber
   101→- Error/lost: red
   102→- Active optical beacon: warm white / pale cyan
   103→- Technical accent: muted cyan-blue
   104→
   105→Do not use cyan/purple gradients.
   106→

   138→
   139→## 2.3 Visual Materials
   140→
   141→Use subtle depth through:
   142→
   143→- 1px borders
   144→- 8–12px radius
   145→- 10–25px shadows
   146→- very subtle backdrop blur only where useful
   147→- slightly different surface elevations
   148→
   149→Avoid:
   150→- giant shadows,
   151→- inflated cards,
   152→- floating widgets with excessive blur,
   153→- glossy effects.

   194→
   195→The main application should use a **three-column operations layout**.
   196→
   197→```text
   198→┌──────────────────────────────────────────────────────────────────────────────┐
   199→│ TOP SYSTEM BAR                                                               │
   200→├───────────────┬───────────────────────────────────────────┬──────────────────┤
   201→│               │                                           │                  │
   202→│ LEFT CONTROL  │            PRIMARY WORKSPACE              │ RIGHT TELEMETRY  │
   203→│ PANEL         │                                           │ PANEL            │
   204→│               │     Camera / Scene / 3D workspace        │                  │
   205→│               │                                           │                  │
   206→│               │                                           │                  │
   207→├───────────────┴───────────────────────────────────────────┴──────────────────┤
   208→│ TIMELINE / ERROR PLOT / STATE HISTORY                                       │
   209→├──────────────────────────────────────────────────────────────────────────────┤
   210→│ EVENT LOG / SYSTEM CONSOLE                                                   │
   211→└──────────────────────────────────────────────────────────────────────────────┘
   212→```
   213→
   214→The desktop viewport should be optimized around:
   215→
   216→```text
   217→1440 × 900
   218→1600 × 1000
   219→1920 × 1080
   220→```
   221→
   222→Do not design around mobile first. This is an engineering desktop application.
   223→
   224→A responsive fallback may support smaller displays, but the primary experience is desktop.

  1961→# 48. Definition of Frontend Done
  1962→
  1963→The frontend is considered complete when:
  1964→
  1965→- The main dashboard clearly shows the live camera feed.
  1966→- The moving beacon is visually obvious.
  1967→- Detection, prediction and camera center overlays are visible.
  1968→- Camera pan/tilt movement is visible.
  1969→- Simulation controls are configurable without editing files.
  1970→- Disturbances can be enabled/disabled from the UI.
  1971→- SEARCH/CANDIDATE/ACQUIRE/TRACK/PREDICT_REACQUIRE state is visible.
  1972→- FPS, acquisition, error, lock, loss, reacquisition and processing metrics are visible.
  1973→- PS-169 benchmark targets are displayed separately from internal thresholds.
  1974→- Error and trajectory charts update during runs.
  1975→- Event logs show meaningful state transitions.
  1976→- Results can be exported.
  1977→- MP4 benchmark mode is accessible.
  1978→- Ground-truth availability is explicitly communicated.
  1979→- Replay can visualize a completed run.
  1980→- The 3D view shows camera pose, FOV, beacon and trajectory.
  1981→- The application never implies that recorded MP4 footage was physically re-pointed.
  1982→- The UI remains responsive during a live run.
  1983→- The visual language looks like professional engineering software rather than a generic AI/SaaS dashboard.
